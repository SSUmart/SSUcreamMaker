# 온글 평가 잣대·정답지·비교 계획 분석

교수님 피드백("목표를 잣대로 바꾸고, 정답지를 만들고, 기존 서비스와 같은 과제로 견줄 것")을 기준으로 온글의 지금 평가 상태를 점검하고, 발표와 워크숍까지 할 일을 정리했다. 근거는 `docs/PROPOSAL.md` 9장(평가 계획), `eval/` 평가 도구, `eval/results/`의 실행 기록(2026-10-21~24)이다.

## 1. 피드백이 묻는 두 질문

| 질문 | 지금 답할 수 있나 | 이유 |
|---|---|---|
| ① 온글이 **잘 되는가** | 일부만 | 읽기·점자·상세 이미지는 정답지와 점수가 있다. 자동 보완·요약·질문 응답은 정답지가 없고, 목표 칸이 "측정 후 설정"으로 비어 있다 |
| ② 기존 스크린리더**보다 나은가** | 못 함 | 같은 과제로 NVDA·센스리더와 견준 결과가 하나도 없다. 9장의 "실사용" 지표는 "단축 여부"만 적혀 있다 |

시연이 잘 돌아가는 것은 ①의 증거가 아니고, 우리가 만든 정답표와 100% 일치하는 것도 ②의 증거가 아니다. 발표 전에 ②를 채우는 것이 가장 급하다.

## 2. 지금 가진 것과 빈칸

| 기능 | 잣대 | 정답지 | 결과 |
|---|---|---|---|

| 탐색 명령(R2) | 기대 위치로 이동한 명령 비율 | E2E 34개 항목 | 34/34 |

| 상세 이미지(A2) | 글자 인식률(놓치지 않은 비율), 분류 정확도, 걸린 시간 | 4개 사례, 정답 문구 53개 | 아래 표 |

### 2-2. 빈칸과 약점

| # | 문제 | 왜 문제인가 |
|---|---|---|
| G1 | 기존 스크린리더와 견준 결과 없음 | 피드백의 핵심 요구. "더 낫다"를 말할 근거가 없다 |
| G2 | 자동 보완(A1)·요약(A3)·질문 응답(A4) 정답지 없음 | AI 기능 4개 중 3개를 못 잰다. `e2e-summary-qa`는 가짜 AI로 **동작만** 확인한다 |
| G3 | 상세 이미지 잣대가 "놓친 것"만 잼 | 정답 문구가 결과 **어딘가에** 나오면 맞음. 틀린 숫자나 지어낸 문장(헛짚은 것)은 자동으로 못 잡고, 실행 기록에도 사람 확인 결과가 없다 |
| G4 | 정답지가 작고 대부분 우리가 만든 페이지 | 사례 4개 중 실제 쇼핑몰은 1개. 읽기 162/162도 우리가 만들고 고쳐 온 페이지 기준이다. 개발하며 맞춘 문제로 시험 보는 셈이라(과적합) 처음 보는 페이지에서는 점수가 떨어질 수 있다 |
| G5 | 정답지를 한 사람이 만듦 | 정답 자체가 틀렸거나 애매한지 확인할 방법이 없다 |
| G6 | 목표치의 근거가 없음 | "자동 보완 70% 이상"은 어디서 왔는지 설명할 수 없다. 기준선(기존 방법의 점수)에서 목표를 정해야 한다 |
| G7 | 한 번만 실행, 지연은 평균조차 없음, 결과에 모델·코드 버전 기록 없음 | 2-1 표처럼 실행마다 다른데 원인을 가릴 수 없다. 지연은 p50(중간값)·p95(느린 쪽)로 봐야 한다 |
| G8 | AI 채점을 쓰지 않았고, 쓸 때의 치우침 대책도 없음 | 요약·질문 응답은 문장이라 기계적 비교가 어렵다. AI 채점을 쓰려면 사람 채점과 맞는지 먼저 보여야 한다 |

## 3. 목표를 잣대로 바꾸기

기능마다 "무엇을 묻는가 → 무엇으로 재는가 → 어디까지 가면 충분한가 → 무엇과 견주는가" 순서로 정한다.

### 3-1. 잣대 고르는 기준

| 잣대 | 언제 쓰나 | 온글에서 |
|---|---|---|
| 놓친 비율 (재현율의 반대) | 빠뜨리면 안 되는 정보가 있을 때 | 상세 이미지의 가격·주의사항, 요약의 핵심 사실 |
| 헛짚은 비율 (정밀도의 반대) | 틀린 정보가 해로울 때 | 상세 이미지의 틀린 숫자, 자동 보완의 엉뚱한 이름 |
| 지어낸 답 건수 | 근거 없는 말이 위험할 때 | 요약·질문 응답에서 페이지에 없는 내용. 답이 없는 질문에 답한 경우 |
| 위험한 오답 건수 | 특정 실수의 비용이 클 때 | 삭제·취소 버튼을 다른 동작으로 읽음 (오답 하나가 주문 취소로 이어짐) |
| 걸린 시간 p50/p95 | 기다림이 흐름을 끊을 때 | 자동 보완·요약·답변, 첫 음성까지 |
| 과제 성공률·걸린 시간·키 입력 수 | 사람이 실제로 해내는지 볼 때 | 기존 스크린리더와 견주기 |
| 사람이 매긴 점수 (1~5 기준표) | 정답이 하나가 아닐 때 | 요약 품질, 자동 보완 이름이 "쓸 만한가" |

시청각장애인은 점자로만 읽으므로 **틀린 정보를 확인할 다른 통로가 없다.** 그래서 온글은 "놓친 것"보다 "헛짚은 것·지어낸 것"을 더 엄하게 잡는다.

### 3-2. 기능별 잣대와 목표 (제안)

| 기능 | 묻는 것 | 주 잣대 | 보조 잣대 | 목표 (제안) | 견줄 대상 |
|---|---|---|---|---|---|
| 읽기 엔진 R1 | 처음 보는 페이지도 바르게 읽나 | 정답표 일치율 | 틀림·빠짐·더 읽음 건수 | 평가용 쇼핑몰 100% 유지, **처음 보는 실제 페이지 95% 이상** | NVDA가 같은 페이지를 읽은 결과 |
| 점자 R5 | 규정대로 바꾸나 | 규정 예문 일치율 | NVDA(liblouis) 차이 분석 | 100% 유지 | NVDA 점자 출력 |
| 자동 보완 A1 | 이름 없는 요소에 맞는 이름을 붙이나 | 사람 판정 정답률(맞음/비슷함/틀림) | **위험한 오답 0건**, "모르겠음" 비율, 시간 p95 | 정답률은 기준선 측정 후 정함, 위험한 오답 0건 | NVDA("버튼"만 읽음) |
| 상세 이미지 A2 | 그림 속 정보를 빠짐없이, 틀림없이 전하나 | 놓친 비율 + **헛짚은 비율** | 분류 정확도, 시간 p50/p95, 실패율 | 놓침 10% 이하, 틀린 숫자·지어낸 문장 0건 | NVDA(아무것도 안 읽음), **일반 AI 앱에 그림을 직접 물어보기** |
| 요약 A3 | 핵심을 담고 없는 말을 안 하나 | 핵심 사실 포함 비율 | 지어낸 내용 건수, 사람 점수 | 포함 80% 이상, 지어낸 내용 0건 | NVDA로 처음부터 읽기(걸린 시간) |
| 질문 응답 A4 | 맞게 답하고, 모르면 모른다고 하나 | 답 있는 질문 정답률 | **답 없는 질문에 지어낸 답 0건**, 근거 위치 정확도 | 정답률 기준선 측정 후 정함 | NVDA로 직접 찾기 |
| 실사용 | 기존 스크린리더보다 빨리, 정확히 해내나 | 과제 성공률 | 걸린 시간, 키 입력 수, 틀린 답을 믿은 횟수, 과제 뒤 난이도 점수 | 성공률 높고 시간 짧음 | NVDA, 센스리더 |

목표치는 **기준선을 먼저 재고** 정한다. 예를 들어 NVDA가 상세 이미지 과제를 0% 해내면 "이긴다"는 당연하므로, 더 센 비교 대상(일반 AI 앱에 직접 물어보기)과 견줘야 의미가 있다(4장).

## 4. 견줄 기존 방법

| 비교 대상 | 왜 | 무엇을 견주나 |
|---|---|---|
| NVDA (Windows, 무료) | 국내외에서 널리 쓰고 누구나 설치 가능. 온글 키 체계의 기준 | 읽기 정확성, 과제 수행 |
| 센스리더 | 국내 시각장애인이 가장 많이 쓰는 스크린리더 | 과제 수행 (구할 수 있으면) |
| 스크린리더 + 일반 AI 앱 | 지금 시각장애인이 그림 속 글자를 읽을 때 실제로 쓰는 우회 방법(캡처해서 AI 앱에 묻기). 온글의 AI 기능과 가장 정면으로 겨루는 상대 | 상세 이미지·질문 응답의 정확도와 걸린 시간 |
| 사람의 도움 | 기준선의 상한 | (선택) 정답지 작성에 쓰임 |

"같은 조건"으로 견주려면 다음을 맞춘다.

- 같은 PC(Windows), 같은 크롬, 같은 페이지 버전(평가용 쇼핑몰은 고정, 실제 쇼핑몰은 저장본이나 날짜 기록)
- 같은 과제 문장과 같은 성공 기준(정답지에 미리 적음)
- 같은 연습 시간: 온글을 처음 쓰는 사람은 NVDA에 익숙한 사람보다 불리하다. 연습 시간을 같게 하고, 익숙함 차이는 한계로 적는다
- 순서 효과 상쇄: 절반은 NVDA→온글, 절반은 온글→NVDA. 같은 과제를 두 번 하면 답을 외우므로 난이도가 비슷한 과제 묶음 A·B를 만들어 엇갈려 배정
- AI 결과 캐시는 끄고 잰다(시연용 캐시와 구분)

### 4-1. 두 단계로 견주기

**1단계: 출력 비교 (사람 없이, 이번 발표용)**
같은 페이지에서 각 스크린리더가 읽어 주는 글을 모아 정답 정보 중 몇 개가 전달됐는지 센다.
- NVDA는 "음성 뷰어(Speech Viewer)"로 읽은 글을 기록할 수 있다. 평가용 쇼핑몰을 처음부터 끝까지 읽혀 기록을 남긴다
- 온글은 이미 읽기 목록을 뽑는 도구(`reader:accuracy`)가 있다
- 잣대: 과제 정답 정보(할인가, 식기세척기 가능 여부, 교환 기한 등) 중 읽어 준 글에 들어 있는 비율, 이름 없는 요소 5개를 무엇으로 읽었나

**2단계: 과제 비교 (사람이 직접, 12주차까지)**

| 과제 | 정답 | 어디에 있나 | 주로 견주는 기능 |
|---|---|---|---|
| 이 상품의 할인가는? | 24,900원 | 상세 이미지 | A2 |
| 식기세척기에 넣어도 되나? | 안 됨 | 상세 이미지 | A2·A4 |
| 교환·반품은 며칠 안에 신청? | 7일 이내 | 상세 이미지·배송 표 | A2·A4 |
| 상품을 공유하는 버튼을 눌러라 | 공유 버튼 누름 | 이름 없는 버튼 | A1 |
| 고른 옵션을 초기화하라 | 휴지통 버튼 누름 | 이름 없는 버튼(파괴적) | A1 |
| 첫 리뷰에 "도움돼요"를 눌러라 | 해당 버튼 누름 | 이름 없는 버튼 | A1 |
| 리뷰에서 가장 많이 나온 불만은? | (정답지에 적음) | 긴 리뷰 목록 | A3 |
| 보증 기간은 몇 년인가? | "페이지에 없음" | 없음 (답 없는 질문) | A4 지어낸 답 |

재는 것: 성공 여부, 걸린 시간, 키 입력 수, 틀린 답을 맞다고 믿은 횟수, 과제마다 난이도 점수(1~7점, 한 문항).

**참가자**: 실제 시각장애인 사용자가 가장 좋다(PROPOSAL 12장 "사용자 테스트 협력 기관" 미결). 구하지 못하면 1차로 팀원·반 학생이 화면을 가리고 하되, **눈으로 보던 사람은 스크린리더 사용자를 대표하지 못한다**는 한계를 결과와 함께 적는다.

## 5. 정답지 만드는 법

### 5-1. 원칙

1. **개발용과 시험용을 나눈다.** 지금 사례 4개와 평가용 쇼핑몰은 개발하며 맞춘 "연습 문제"다. 시험용은 새로 모으고, 점수가 나쁘게 나와도 시험용 페이지를 보고 프롬프트를 고치지 않는다(고치면 그 페이지는 개발용으로 옮긴다)
2. **정답은 결과를 보기 전에 적는다.** AI 결과를 보고 정답을 적으면 정답이 AI 쪽으로 기운다
3. **두 사람이 따로 적고 맞춰 본다.** 둘이 다른 곳은 애매한 문제다. 합의하거나 빼고, 일치율을 함께 기록한다
4. **짧고 확실한 단위로 적는다.** 문장 전체보다 숫자·단어(기존 `cases.json` 방식). 요약은 "핵심 사실" 목록으로
5. **날짜와 출처를 남긴다.** 실제 쇼핑몰은 바뀐다. 페이지 저장본(또는 스크린샷)과 작성 날짜를 함께 둔다

### 5-2. 기능별 정답지 크기와 형식 (제안)

| 기능 | 크기 | 형식 |
|---|---|---|
| 읽기 R1 | 처음 보는 실제 페이지 3개 (쇼핑몰, 뉴스, 공공기관) | 기존 `shop-expected.json`과 같음 |
| 자동 보완 A1 | 이름 없는 요소 40개 (실제 쇼핑몰에서 수집하거나, 이름 있는 요소의 이름을 지워 만듦). 그중 삭제·취소류 10개 이상 | 아래 예시 |

### 5-3. 상세 이미지 잣대 보강

지금 `score.js`는 정답 문구가 결과에 있으면 맞음으로 센다. 다음을 더한다.

- **헛짚은 것**: 결과의 각 줄을 사람이 "맞음 / 틀림(숫자·단위 오류) / 지어냄(그림에 없음)"으로 판정. 처음에는 결과 JSON을 표로 뽑아 사람이 표시하고, 쌓이면 AI 채점과 맞춰 본다(6장)
- **위험한 문구**: 가격·알레르기·주의사항처럼 틀리면 해로운 정답에 표시하고 따로 집계
- **반복 실행**: 사례마다 5번 돌려 평균, 최저, 실패 횟수, 시간 p50/p95
- **실행 조건 기록**: 결과 JSON에 공급자·모델 이름, 커밋, 날짜를 함께 저장

## 6. AI 채점과 치우침

요약·질문 응답·자동 보완 이름처럼 답이 문장이면 사람이 일일이 채점하기 어려워 AI에 맡기게 된다. AI 채점에는 다음 치우침이 알려져 있다.

| 치우침 | 내용 | 온글에서 생길 수 있는 일 | 대책 |
|---|---|---|---|
| 자기 선호 | 같은 회사 모델이 만든 답을 후하게 줌 | Gemini가 만든 요약을 Gemini가 채점 | 만든 모델과 다른 공급자로 채점 (예: NIM 모델 또는 다른 회사 모델) |
| 길이 선호 | 길고 자세한 답에 점수를 더 줌 | 점자용으로 짧게 쓴 온글 답이 손해 | 기준표에 "짧을수록 좋음" 명시, 점수 대신 사실 단위 판정 |
| 위치 선호 | 두 답을 견줄 때 먼저(또는 나중에) 나온 답을 고름 | 온글 대 기존 방법을 나란히 채점할 때 | 순서를 바꿔 두 번 채점, 결과가 뒤집히면 무승부 |
| 점수 몰림 | 1~10점이면 7~8점에 몰림 | 차이가 안 보임 | 맞음/틀림처럼 두세 단계 판정, 정답지를 함께 줌 |
| 겉모양 속음 | 자신 있는 말투, 깔끔한 형식에 속음 | 지어낸 답이 그럴듯하면 맞다고 함 | "정답지에 없는 사실이 있나"를 따로 묻기 |
| 실행마다 다름 | 같은 답도 채점이 바뀜 | 점수가 흔들림 | 온도 0, 3번 채점해 다수결 |

**원칙: AI 채점은 사람 채점과 맞는지 먼저 보여 준 뒤에만 쓴다.** 표본 일부(예: 40개)를 사람 2명과 AI가 함께 채점해 일치율(Cohen's kappa 포함)을 보고, 사람끼리의 일치율과 비슷할 때만 나머지를 AI에 맡긴다.

### 6-1. 워크숍 4번 준비 (1조 AI 채점 대 반 전체 사람 채점)

1. 평가용 쇼핑몰에서 요약 1개, 질문 응답 10개(답 없는 질문 3개 포함), 자동 보완 5개의 실제 결과를 뽑는다
2. 일부러 섞는다: 맞는 답, 숫자가 틀린 답, 그럴듯하게 지어낸 답, 길지만 핵심이 빠진 답
3. 미리 AI 채점: 같은 기준표로 Gemini 채점과 다른 공급자 채점을 각각 돌린다
4. 워크숍에서 반 전체가 같은 기준표로 채점(종이나 설문)
5. 견줄 것: 사람 대 AI 일치율, 갈린 문항, Gemini가 자기 답을 후하게 줬는지, 긴 답을 후하게 줬는지

이 결과는 "AI 채점을 어디까지 믿어도 되는가"를 보여 주는 자료이자 1조 발표 내용이 된다.
